# Integrations

Docker installations can connect optional services from **Settings > Integrations**. Every integration is disabled by default, and secrets are kept write-only in API responses.

## At a glance

| Integration | What it adds | Data handling |
| --- | --- | --- |
| AdGuard Home | Network-wide and per-device DNS destinations and blocked totals | Stores aggregate counters, not raw DNS responses |
| Pi-hole v6 | DNS destinations, blocked totals, and DHCP client discovery | Stores aggregate counters and current lease identity data, not raw DNS responses |
| Technitium DNS Server v15+ | DNS destinations and blocked totals, with optional DHCP enrichment | Stores aggregate counters and selected lease identity data, not raw DNS responses |
| DHCP lease source | IPv4 address and hostname evidence from dnsmasq, Kea, or ISC DHCP files | Imports active leases; does not infer online presence or delete devices on expiry |
| ASUSWRT | Router client discovery, IPv4/hostname/vendor enrichment, and available connection details | Reads structured client data; preserves user-managed identity and scanner presence |
| OpenWrt / LuCI | IPv4 DHCP leases, neighbor-derived host hints, and multi-radio Wi-Fi observations | Reads HTTP ubus inventory; existing device identity, IP and presence are unchanged |
| Speedtest Tracker | Latest internet result and health on the dashboard and Network Map Internet tile | Stores settings and latest processed health state, not result history |
| HomeBox | Search and link an existing inventory item to a device | Stores the linked item ID; does not synchronize inventory |
| Docker inventory | Running containers, health, addresses, restarts, and published ports | Reads the local Docker engine from the scheduler |

## ASUSWRT

ASUSWRT appears under **Settings > Integrations > Network controllers**. It reads the router's local HTTP(S) client-list interface, using the same login and read-hook protocol used by the [AsusRouter project](https://github.com/Vaskivskyi/asusrouter). No SSH, shell commands, HTML/JavaScript scraping, router configuration changes, or firmware-specific scripts are used.

### Router and firmware compatibility

The integration targets stock ASUSWRT and ASUSWRT-Merlin firmware that expose JSON `login.cgi` and `appGet.cgi` endpoints with the `get_clientlist()` hook. This is a firmware-dependent interface, not an ASUS-guaranteed public API. Not every model or firmware version exposes the same fields; unsupported responses fail without changing devices. Compatibility has been tested against representative structured responses, not every physical router model.

### Setup and authentication

1. Enable ASUSWRT, enter the router's base URL (for example `https://192.168.50.1:8443`), and enter its local administrator username and password. Do not use an ASUS cloud account, a URL containing credentials, or a web-panel page path.
2. Keep **Verify TLS certificate** enabled. For self-signed HTTPS, trust the router certificate in both backend and scheduler containers. Disabling verification is an explicit option for a trusted LAN only. HTTP sends the login authorization without encryption and should never be used over an untrusted network. Do not expose the router management interface to the internet for this integration.
3. Select **Test connection**. Testing authenticates, reads the client list and available router model/firmware, then logs out without modifying devices.
4. Optionally enable **Create devices from router clients**. This is off by default; otherwise only matching existing devices are enriched.
5. Save integration settings, then choose **Sync now**. The scheduler repeats sync at the saved interval (1 to 1440 minutes, default 5).

The integration performs only read operations but the router account itself can have administrator privileges. Protect the LanGuard database and its backups accordingly. Passwords are write-only in API responses, session tokens are kept in memory, and diagnostics do not store credentials or raw responses. Changing the router URL or username requires re-entering its password; a connection test will not reuse a saved password for a different target. Redirects are not followed. Each attempt uses one login without automatic authentication retries and closes the session afterwards. After a login refusal, automatic attempts pause to avoid worsening router lockout. Resolve credentials, CAPTCHA, or lockout in the router, then explicitly test and sync manually, or save corrected credentials.

### Imported data and limitations

Only clients explicitly reported as active with valid private IPv4 and unicast MAC addresses are imported. Cached/offline entries, invalid records, ambiguous duplicate IPs/MACs, and IPv6 entries are skipped. User-managed Known-device identity, archived devices, stronger hostname sources, newer IP observations, and IP-conflict evidence are preserved. Existing merged interfaces remain matched by their individual MACs rather than creating another logical device.

Available router-reported name, model, Ethernet/Wi-Fi band, SSID, signal strength, and observation time appear on the device page. These are timestamped observations, not a live link monitor or a verified topology. Missing optional fields are not invented. A router record never marks an existing device online/offline, advances its scan last-seen time, or removes it when it disappears; new devices start as Unknown and not Online until LanGuard verifies presence.

This integration does **not** collect DNS query history, blocked-domain statistics, or DHCP lease expiry information. Continue using AdGuard Home, Pi-hole, or Technitium for DNS activity, or the independent DHCP lease source when actual lease-file evidence is needed. Client-list responses are limited to 5 MiB and 5,000 entries. Only selected normalized observations and sync summaries are stored.

## OpenWrt

Under **Settings > Integrations > Network controllers**, enable **OpenWrt / LuCI**.
Enter the router's HTTP(S) origin (or its `/ubus` URL) and dedicated rpcd
credentials. Use **Test connection** to check access without changing inventory,
then save and use **Sync now** or let the scheduler run.

This integration uses the [HTTP ubus JSON-RPC API](https://openwrt.org/docs/techref/ubus),
not the legacy LuCI `/cgi-bin/luci/rpc` API. Compatibility is detected by
available methods and permissions, not a firmware version check. The router
needs an HTTP ubus endpoint (typically `uhttpd-mod-ubus`) and LuCI inventory RPCs
(`rpcd-mod-luci`). Wireless associations additionally require
`rpcd-mod-iwinfo`. Package availability and responses vary by firmware build.

Have the router administrator assign a dedicated rpcd login a **read-only**
ACL group (for example, `languard-inventory`), with no write permissions. The
inventory permissions for that group are:

```json
{
  "languard-inventory": {
    "description": "LanGuard read-only inventory",
    "read": {
      "ubus": {
        "luci-rpc": ["getDHCPLeases", "getHostHints", "getWirelessDevices"],
        "iwinfo": ["assoclist"]
      }
    }
  }
}
```

Keep `/ubus` reachable only from the management network. Prefer HTTPS with a
trusted certificate and TLS verification enabled. HTTP exposes credentials to
the network; disabling TLS verification removes server identity protection.
LanGuard does not use SSH, edit router configuration, or execute commands.
Automatic login pauses after authentication failure; correct the settings and
run a manual sync to resume. If a method is unavailable, the integration reports
it and uses the other supported sources.

OpenWrt observations show reported lease/interface information, IPv4/IPv6 host
hints, and Wi-Fi associations with interface, radio, SSID, logical networks and
signal where available. Host hints can include cached neighbors, static leases,
and router-local interfaces. They are not proof of current reachability.
Wi-Fi observations cover access points reported by the configured router, not
other mesh nodes. Observations are timestamped; absent clients are not marked
offline or removed. Existing device identity, IP and scan status are preserved.
Optional creation is off by default and uses only unambiguous IPv4 DHCP leases;
it never marks devices online.

## DHCP lease source

This independent integration reads a DHCPv4 lease file. It works alongside any DNS provider and does not require a Pi-hole or Technitium installation. It supports:

- dnsmasq lease files with Unix expiry timestamps; zero means no expiry.
- Kea DHCPv4 memfile CSV files, including appended updates and released or reclaimed entries.
- ISC `dhcpd.leases` files, including UTC or epoch end times and leases ending `never`.

For Kea and ISC journals, the last record for an IP address wins, including records that release it. Expired, released, invalid, public, multicast, and IPv6 entries are not imported. The integration supports standard timestamp-based dnsmasq files, not builds that store relative lifetimes with `HAVE_BROKEN_RTC`.

### Mount the lease directory

Mount a dedicated directory read-only into both the backend and scanner services. Mount the directory rather than an individual file so DHCP file replacement and rotation remain visible:

```yaml
services:
  backend:
    volumes:
      - ./dhcp:/data/dhcp:ro
  scanner:
    volumes:
      - ./dhcp:/data/dhcp:ro
```

These entries are additional volumes; keep the existing database and static volumes. Files must be UTF-8, regular files, no larger than 5 MiB, and contain at most 50,000 records. Paths are relative to `/data/dhcp`; absolute paths and symlinks escaping that directory are rejected. To use a different directory, set `DHCP_LEASE_DIRECTORY` to the same absolute directory in both services.

A remote DHCP server can periodically copy or export its lease file to this directory. Preserve its modification timestamp and replace the copy atomically. The integration does not connect over SSH or call remote DHCP APIs.

### Configure and synchronize

1. Open **Settings > Integrations > Network controllers > DHCP lease source**.
2. Enable it, choose the file format, and enter the relative filename, such as `dnsmasq.leases`, `kea-leases4.csv`, or `dhcpd.leases`.
3. Choose the synchronization interval (1 to 1440 minutes). Leave **Create devices from leases** off to enrich existing devices only.
4. **Test source** validates the current filename and format without saving settings or changing devices.
5. Save settings, then select **Sync now**, or let the scheduler synchronize automatically. The latest result shows active lease, created, updated, and conflict counts.

Only active IPv4 leases with valid unicast MAC addresses provide evidence. Optional new devices are Unknown and are not marked Online. Known device names and hostnames are preserved. Existing controller-provided and direct-discovery hostnames take priority over this generic source. Existing identities are matched by MAC, so the same lease reported by a controller does not create another device.

The file modification time is used as the observation time. Older snapshots do not replace newer IP observations. Recent competing MAC addresses on the same IP are flagged using LanGuard's identity-conflict handling, without reassigning that IP or closing the competing assignment. Ambiguous multiple active IPs for one MAC are skipped. Lease expiry or disappearance never deletes a device or changes its presence; normal scanning remains responsible for availability.

The integration is disabled by default. Saved configuration, the last sync result, and a sanitized error are stored; raw lease files are not copied into the database. A malformed, oversized, unreadable, or changing file fails before modifying devices. No extra network scan is started by a DHCP sync.

## Docker inventory

LanGuard can inventory running containers on the same Docker engine that runs its scheduler. It reads metadata only; LanGuard does not provide start, stop, restart, logs, terminal, deployment, or configuration actions. Remote Docker hosts are not supported by this integration.

### Docker socket access

The current Compose file mounts the local Docker socket into the scheduler service:

```yaml
services:
  scanner:
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock:ro
```

Existing installations must add this volume and recreate the scheduler container. A Docker socket is highly privileged even when the bind mount is marked read-only because API calls control access, not filesystem write permissions. LanGuard limits its implementation to `GET` requests and mounts the socket only into the scheduler. Do not expose unauthenticated Docker TCP port `2375`.

### Configure inventory

1. Make sure the Docker server already exists as a LanGuard device.
2. Open **Settings > Integrations > Docker inventory**.
3. Select that device, enter a display name, choose the synchronization interval, and save.
4. The scheduler queues the first synchronization automatically. **Sync now** requests another run within the scheduler's next one-minute check.
5. Open **Docker** from the main navigation to inspect containers and published ports across the configured host.

The scheduler checks once per minute and synchronizes when the configured interval is due. Newly discovered containers and newly published host ports are recorded in device history.

Bridge and host-network containers remain associated with their Docker host. Containers attached through `macvlan` or `ipvlan` receive independent LAN addresses; when an address matches a LanGuard device, the container is linked to that device automatically.

Port mappings distinguish the host port from the internal container port. For example, **Host 8080 → Container 80** means connections to port `8080` on the Docker host are forwarded to port `80` inside the container. A check mark means the LanGuard network scanner also found that host port reachable; it is confirmation of the mapping, not a deployment warning. Docker metadata and LAN reachability do not prove Internet exposure.

## AdGuard Home

1. Enable query logging in AdGuard Home.
2. Enable **AdGuard Home** in LanGuard.
3. Enter its URL and credentials, then select **Test connection**.
4. Save and select **Sync now** for the first import.
5. Open the central **DNS Activity** page or a device's **DNS activity** tab.

The scheduler imports aggregated counters per device, domain, and query type. Each query is matched against the device that owned the client IPv4 address at the query time, so later DHCP changes or address reuse do not move activity between devices. Queries without one reliable historical owner remain in unmatched-client diagnostics instead of being guessed.

The configured retention period removes old DNS aggregates. IP assignment history is independent of event and DNS retention and remains available for the lifetime of the device. After upgrading from an older LanGuard release, current assignments begin when the migration runs; LanGuard does not infer earlier ownership that it did not observe.

> **Device attribution:** AdGuard Home must record the originating device IP. If all requests reach it through the router, LanGuard can associate the activity only with that router. Configure DHCP or clients to use AdGuard Home directly when device-level attribution is required.

## Pi-hole

Pi-hole v6 is supported as an alternative to AdGuard Home. Only one DNS activity provider can be enabled at a time so the same query is not counted twice.

1. In Pi-hole, create an application password under **Settings > Web interface / API**.
2. Enable **Pi-hole** in **Settings > Integrations > Network services**.
3. Enter the Pi-hole URL and application password, then select **Test connection**.
4. Save and select **Sync now** for the first import.
5. Open the central **DNS Activity** page or a device's **DNS activity** tab.

LanGuard uses the supported Pi-hole v6 API. It imports aggregated DNS counters and can optionally read current DHCP leases; it does not mount Pi-hole databases or configuration files. Queries are attributed using LanGuard's historical IP ownership at the query time. **Sync DHCP leases** enriches existing devices by MAC address. **Create devices from leases** is a separate opt-in for adding unmatched valid leases as Unknown devices. A known device's name, hostname, icon, and other user-managed identity remain protected.

Pi-hole is not a presence monitor. A lease can be active while a device is away, and a missing lease does not prove that a device is offline. LanGuard therefore never marks a device offline merely because it is absent from Pi-hole.

> **Device attribution:** Pi-hole must see each originating client IP. DNS requests forwarded by a router are attributed to that router rather than guessed. Pi-hole DHCP discovery is available only when Pi-hole itself has active lease data.

## Technitium DNS Server

Technitium DNS Server v15 or later is supported as an alternative to AdGuard Home and Pi-hole. Only one DNS activity provider can be enabled at a time.

1. Install and enable a compatible Query Logs app in Technitium. LanGuard discovers the active query-log implementation dynamically, so SQLite, PostgreSQL, MySQL, and SQL Server-backed apps are supported when they expose Technitium's Query Logs API.
2. Create a Technitium API token with **Logs: View** permission. Add **DHCP: View** only when DHCP lease synchronization is required.
3. Enable **Technitium DNS Server** in **Settings > Integrations > Network services**.
4. Enter the Technitium web-console URL and API token, then select **Test connection**.
5. Save and select **Sync now** for the first import.

LanGuard sends the token only in the `Authorization: Bearer` header. Use HTTPS when Technitium is reached across an untrusted network; plain HTTP should be limited to a trusted local network. The integration is read-only and does not change zones, server settings, DHCP scopes, or DNS applications.

DNS queries are imported incrementally and attributed using LanGuard's historical IP ownership at query time. Queries that cannot be assigned reliably remain in unmatched-client diagnostics. Optional DHCP synchronization can update the current IP and hostname of an existing unknown device by MAC address without changing user-managed known-device identity or presence. Creating Unknown devices from leases is a separate opt-in setting, and lease data never marks a device online or offline.

## Speedtest Tracker

1. Create a Speedtest Tracker API token with the `results:read` ability.
2. Enable **Speedtest Tracker** in LanGuard.
3. Enter its URL and token, test the connection, and save.

LanGuard displays download, upload, ping, packet loss, health, and test time. Dashboard responses use a five-minute in-memory cache; a manual dashboard refresh requests fresh data. When health notifications are enabled, the scheduler checks for a newly scored result every five minutes.

Configure thresholds in Speedtest Tracker first. Unscored results and temporary connection failures do not send a health-change notification.

The [Network Map Internet node](/docs/network-map#internet-and-speedtest) reuses the latest measurement, including its timestamp. A positive completed test no older than 15 minutes can verify access at test time; enabling the integration alone does not prove connectivity. Older measurements remain labeled as historical, and a failed API request does not mean the Internet is offline. This is not a live or per-WAN reachability probe.

## HomeBox

LanGuard supports the `/api/v1/entities` API used by HomeBox v0.26.2. Releases that expose only the older `/items` API are not supported.

1. Create a HomeBox API key for an account with access to the intended inventory.
2. Enable HomeBox, enter its URL and API key, test, and save.
3. Open a LanGuard device, select **Edit device**, search for a HomeBox item, and save.
4. Use **Open in HomeBox** from the device page.

Search is proxied through the backend and requires device-edit permission. LanGuard does not create or update HomeBox items, and it does not copy documents, purchase records, or warranties. Clearing the selected item removes only the link.

## Automation webhook

The generic webhook channel can deliver enabled events to n8n, Home Assistant, or another HTTPS endpoint. It belongs to notification settings because it follows the same event rules, quiet hours, history, and retry policy as user-facing channels.

See [Notifications](./notifications#automation-webhook) for the payload and signature format.
